# 테스트 하네스: 바뀐 곳에 따라 돌릴 검사

- 목적: CI/CD 없이, PR마다 **바뀐 곳과 관련된 검사만** 직접 돌린다.
- 역할 분담: 이 문서가 "무엇을 돌릴지"를 정하고, `tools/selftest.py`가 검사를 실행한다.
- 갱신: 새 영역(폴더·파일 종류)이나 새 검사가 생기는 PR에서 이 문서를 함께 고치고 맨 아래 변경 이력에 한 줄 남긴다.

## 1. 쓰는 법 (자체 리뷰 단계)

1. 바뀐 파일을 본다: `git diff --name-only dev...HEAD`, 커밋 전이면 `git status --short`도 함께 본다(작업 브랜치는 `dev`에서 딴다, `docs/브랜치_규칙.md`).
2. 아래 분기표에서 해당하는 행을 모두 찾아 그룹을 합친다. `guard`는 항상 넣는다.
3. `python tools/selftest.py <그룹> [<그룹> ...]`을 실행하고, 결과 요약을 PR 자체 리뷰 댓글에 붙인다. `all`은 Docker가 필요한 `devdb`를 뺀 전부다.
4. 표에 없는 경로가 바뀌었으면 먼저 이 문서에 행을 추가하고(필요하면 검사도 만들고) 실행한다.

`analysis/`(개발 외 작업 폴더, git 밖)는 PR이 없다. 고친 뒤 그 자리에서 `python tools/selftest.py analysis`를,
분석 스크립트나 그 출력을 고쳤으면 `data`도 돌린다. 결과는 따로 남기지 않는다.

## 2. 분기표

| 바뀐 경로 | 돌릴 그룹 | 함께 손으로 볼 것 |
|---|---|---|
| 모든 PR | `guard` | 스테이징 목록에 영상·원본 데이터·기록 키 파일이 없는지 |
| `CLAUDE.md`, `AGENTS.md`, `docs/` | `docs` | CLAUDE.md 순서(목표 → 진행 중 → 필수 → 정보 위치), AGENTS.md 범위 규칙이 CLAUDE.md와 같은지 |
| `analysis/` 아래 문서 (PR 없음, 로컬) | `analysis` | 새 파일을 `analysis/README.md` 표에 등록했는지, 바꾼 수치가 원 문서와 맞는지 |
| `analysis/05_데이터_연결/scripts/`, 그 저장 출력(`check_output.txt`, `스키마_프로파일.md`) (PR 없음, 로컬) | `data`, `analysis` | 의도한 변경이면 스크립트를 저장 경로로 다시 돌려 출력도 갱신 |
| `analysis/06_W05_수주약속/scripts/`, 그 저장 출력(`w05_facts_output.txt`) (PR 없음, 로컬) | `data`, `analysis` | 수치를 바꿨으면 `02_관련_DB.md`·`03_문제상황_분석.md`·`04_기초_플랜.md`의 같은 수치도 고친다 |
| `server/` (Go) | `app` (저장소 `server/store/`나 `server/go.mod`를 바꿨으면 `devdb`도) | API를 바꿨으면 화면에서 한 번 불러 본다. 새 의존성은 이유를 PR에 적고 출시 2주 넘은 버전으로 고정한다 |
| `web/` (React·Vite, `package.json`·`package-lock.json` 포함) | `app` | 바뀐 화면을 브라우저로 한 번 연다(`npm run dev`). 새 의존성은 이유를 PR에 적는다 |
| `Dockerfile`, `.dockerignore`, `axhub.yaml` | `app`, `devdb` | 배포 이미지가 Postgres 모드로 뜨는지는 `devdb`가 본다(Docker Desktop 필요). `axhub.yaml`의 `database`를 바꿨으면 다음 릴리스 뒤 사이트 `/api/status`에서 `"store":"postgres"`를 확인한다 |
| `compose.dev.yaml` | `devdb` | 로컬 Docker는 dev 테스트용이다. `ports:`를 넣지 않는다(호스트 포트 공개 금지, `devdb`가 검사) |
| `tools/selftest.py` | 고친 그룹 | 일부러 실패를 넣어 잡히는지 확인하고 리뷰에 적는다 |
| `tools/git-hooks/`, `.gitattributes` | `guard` | 훅에 막을 푸시·통과할 푸시를 직접 넣어 본다(`printf '<ref> <sha> <ref> <sha>' \| sh tools/git-hooks/pre-push <원격> <URL>`), 실제 확인은 `git push --dry-run` |
| 릴리스 PR(`dev` → `main`) | `all`, `devdb` | `docs/브랜치_규칙.md` §4 절차, 배포 뒤 사이트 `/healthz` |
| `.gitignore`, `.claude/`, `.codex/`, `.agents/`, `01_참가자_배포용/` | — | **바꾸지 않는다.** `guard`가 실패하면 되돌린다. `.git/info/exclude`의 `/analysis/` 줄도 지우지 않는다 |
| 표에 없는 경로 | `guard` | 이 문서에 행을 추가한다 |

## 3. 그룹별 검사

| 그룹 | 검사 | 시간 |
|---|---|---|
| `docs` | CLAUDE.md 100줄 이내("진행 중인 작업" 제외) · 개발 규칙 문서(CLAUDE·AGENTS·`docs/`)에 적은 경로가 실제로 있는지 · 병합 충돌 표시(`<<<<<<<`) 없음 | 1초 |
| `analysis` | 색인(`analysis/README.md`·`analysis/TODO.md`)에 적은 경로가 실제로 있는지 · `analysis/` 파일이 모두 README 표에 등록됐는지. 나머지 분석 문서의 없는 경로는 경고만 낸다 | 1초 |
| `data` | `DATA_SCRIPTS`에 등록한 분석 스크립트를 원본으로 다시 돌려 저장 출력과 줄 단위로 비교(재현성). 원본 데이터가 있는 이 PC에서만 돈다 | 10초 |
| `app` | Go: `gofmt -l`·`go vet`·`go test`·`go build` · 화면: `npm run build`(tsc 타입 검사 + Vite, 임시 폴더로) · 빌드한 서버를 DB 주소 없이(메모리 저장소) `127.0.0.1` 빈 포트로 띄워 `/healthz` 200, `/` 200, `/api/status` 200·`"store":"memory"`, 없는 `/api/*` 404(JSON), 화면 주소 새로고침 200 · Dockerfile이 `server/`·`web/`을 복사하고 `.dockerignore`가 둘만 보내는지. Go 1.26+, Node 22.12+, `web/node_modules`(`cd web && npm ci`) 필요 | 6초 |
| `devdb` | 로컬 Docker dev 테스트(`compose.dev.yaml`): compose 설정에 호스트 공개 포트 0개 · Docker 안에서 Postgres 통합 테스트(`go test`, `TEST_DATABASE_URL`) · 배포 이미지(`Dockerfile`)를 Postgres 모드로 띄워 healthcheck 통과 · 같은 내부 네트워크의 컨테이너에서 `/healthz`·`/api/status`(`"store":"postgres"`, `"db":"ok"`) · 실행 중 컨테이너 공개 포트 0개 · 끝나면 `down -v`(DB는 tmpfs라 남지 않음). Docker Desktop 필요, `all`에 없음 | 첫 실행 수 분(이미지 받기), 이후 1분 안팎 |
| `guard` | 보호 경로에 git 변경 없음 · 원본 데이터 72개 파일 해시가 기준(`.git/info/raw_data.sha256`, 11/09 생성, 로컬 전용)과 같음 · 스테이징에 금지 경로(`analysis/`, `web/node_modules/`, `web/dist/` 포함)나 20MB 초과 파일 없음 · `analysis/`가 git 밖(추적 0개, 무시 설정 있음) · 브랜치 규칙(pre-push 훅 있음·LF, `core.hooksPath` 설치, 현재 브랜치 이름, `main`·`dev`에서 스테이징 없음) | 2초 |

- `guard`의 스테이징 검사는 `git add` 뒤에 돌려야 의미가 있다. 커밋 직전에 한 번 더 돌린다.
- `docs`·`analysis`·`data`·`guard`는 원본 자료(`01_참가자_배포용/`)와 `analysis/`(둘 다 git 밖)가 있는 **이 프로젝트 폴더에서** 돌린다. 새로 clone한 곳에서는 경로 확인이 실패한다.

## 4. 구현이 시작되면 추가할 분기 (예정)

| 영역 | 그룹 | 검사 |
|---|---|---|
| 규칙 엔진 | `engine` | 계산을 원본 재계산값과 비교(예: 배치 불량률 11.87%, Masil 현금 하회 구간 7/21~8/21) |
| 시나리오 | `scenario` | 정상·변경·거절 3건을 입력 → 기대 상태·후속 작업·승인 주체와 자동 비교(`analysis/TODO.md` 3. 검증) |
| 화면 | `app` 확장 | 화면마다 실제 작동·모의 처리·설계 단계 표시가 있는지 |

새 폴더가 생기는 PR에서 §2에 행을 추가하고, `tools/selftest.py`의 `GROUPS`에 그룹을 넣는다.

## 5. 이 문서와 실행기를 고칠 때

- 분기표(이 문서)와 검사(실행기)는 같은 PR에서 함께 고친다.
- 분석 스크립트를 추가하면 실행기의 `DATA_SCRIPTS`에 (스크립트, 저장 출력)을 등록한다. 출력은 실행할 때마다 같아야 한다(집합 순회·동률 정렬 주의).
- 경로처럼 보이지만 참조가 아닌 이름은 `NOT_PATHS`에 넣는다.
- 아직 만들지 않은 경로를 문서에 적을 때는 백틱 바로 뒤에 `(예정)`을 붙인다. 예: `` `src/`(예정) ``. 만들고 나면 `(예정)`을 지운다.
- 색인 문서에서는 확장자나 끝 슬래시가 있거나 첫 부분이 실제 최상위 폴더·파일인 것만 경로로 본다(`미확정/잠정` 같은 상태 표기 제외). 명령 예시(`python …`, `git …`)도 건너뛴다.
