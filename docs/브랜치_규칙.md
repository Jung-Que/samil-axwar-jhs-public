## 0. git에 넣는 것과 빼는 것

이슈·PR은 **개발 작업에만** 쓴다. 개발 외 분석 작업과 문서는 이슈로 만들지 않고 폴더를 나눠 git에서 뺀다(11/09 사용자 지시).

| 구분 | 경로 | 흐름 |
|---|---|---|
| 개발(git 대상) | `server.js`, `public/`, `tools/`, `package.json`·`Dockerfile`·`axhub.yaml`, 개발 규칙 문서(`CLAUDE.md`·`AGENTS.md`·`docs/`) | 이슈 → 드래프트 PR → 자체 리뷰 → 병합(§3) |
| 개발 외(git 밖) | `analysis/`: 리서치·문제 분석·기획·분석 스크립트와 출력·할 일(`analysis/TODO.md`) | 이슈·PR 없이 바로 고친다. 확인은 `python tools/selftest.py analysis`(스크립트를 고쳤으면 `data`도) |

- 빼는 방법: 루트 `.gitignore`는 대회 기록 키가 묶여 있어 고치지 않는다. 원본 자료(`01_참가자_배포용/`)처럼 이 PC의 `.git/info/exclude`에 `/analysis/`를 둔다. `guard`가 무시 설정과 추적 0개를 확인하고, `git add -f`로 스테이징해도 잡는다.
- 이름을 `research/`에서 `analysis/`로 바꾼 이유: git이 한 번도 추적하지 않은 폴더라서 옛 커밋(PR #10 이전, 지금의 `main` 포함)을 checkout해도 git이 그 안의 파일을 덮어쓰거나 지우지 않는다. 옛 커밋으로 가면 research/·TODO.md 같은 옛 파일이 잠시 생겼다가 돌아오면 사라질 뿐이다.
- `analysis/`는 GitHub에 백업되지 않는다. 지우거나 덮어쓰지 않게 조심하고, 필요하면 폴더째 따로 복사해 둔다.
- 앱이 분석 결과(예: 업무모델 명세, 시나리오 입력값)를 읽게 되면 그 파일은 개발 쪽(git 대상 경로)으로 옮기고 PR로 관리한다.

## 1. 브랜치 종류

| 브랜치 | 역할 | 만드는 곳 | 병합 대상 | 병합 방식 | 올리는 원격 |
|---|---|---|---|---|---|
| `main` | 배포본. axhub 사이트와 같은 코드 | — | — | 릴리스 PR(`dev` → `main`)만 받는다 | `github`, `origin`(axhub) |
| `dev` | 통합. GitHub 기본 브랜치 | `main`에서 한 번(11/09) | `main` | merge commit | `github` |
| 작업 브랜치 | 이슈 하나의 작업 | **항상 `dev`** | `dev` | squash, 병합 뒤 삭제 | `github` |

- `main`·`dev`에는 직접 커밋·푸시하지 않는다. 두 브랜치는 PR 병합으로만 바뀐다.
- axhub(`origin`)에는 `main`만 올린다. `dev`와 작업 브랜치는 올리지 않는다.
- 급한 수정도 같은 길로 간다: `fix/…` 작업 브랜치 → `dev` → 릴리스. hotfix 브랜치는 따로 두지 않는다.
- 작업 브랜치는 이슈 하나만 담고 짧게 끝낸다. 하루를 넘길 만큼 크면 이슈를 쪼갠다.

## 2. 작업 브랜치 이름

형식: **`<종류>/<이슈번호>-<영문-slug>`**

| 부분 | 규칙 |
|---|---|
| 종류 | 커밋 종류와 같다. `feat` 기능 · `fix` 버그 수정 · `docs` 개발 규칙 문서 · `data` 앱이 쓰는 데이터 적재·변환 · `chore` 설정·도구 · `test` 검사·평가셋(`analysis/` 작업은 브랜치를 만들지 않는다, §0). 여러 종류에 걸치면 주된 것 하나 |
| 이슈번호 | 이슈를 먼저 만든다. 번호 없는 브랜치는 만들지 않는다 |
| slug | 영문 소문자·숫자·하이픈만, 2~5단어. 한글·대문자·밑줄·공백은 쓰지 않는다 |

- 예: `feat/7-engine-v1`, `fix/9-stale-flag`, `chore/10-dockerfile-src`
- 정규식: `^(feat|fix|docs|data|chore|test)/[0-9]+-[a-z0-9]+(-[a-z0-9]+)*$`. 훅의 `BRANCH_RE` 줄 한 곳에 두고 selftest도 그 줄을 읽는다. 규칙을 바꾸면 그 줄과 이 문서만 고친다.
- 11/09 이전 브랜치(`1-research-and-workflow`, `3-w05-plan-domain-db`)는 옛 형식이며 이미 병합·삭제됐다.

## 3. 작업 흐름

```powershell
git switch dev; git pull                       # 최신 dev에서 시작
gh issue create --title "<제목>" --body "<배경·범위·완료 기준·돌릴 검사>"
gh issue develop <번호> --checkout --base dev --name <종류>/<번호>-<slug>
git commit --allow-empty -m "chore: #<번호> 작업 시작"
git push github HEAD
gh pr create --draft --base dev --title "<제목>" --body "Closes #<번호> ..."
# 작업·커밋 → 자체 리뷰(git diff dev...HEAD, 테스트 하네스 분기표의 검사) → 리뷰 댓글 → gh pr ready
gh pr merge <PR번호> --squash --delete-branch
git switch dev; git pull
```

- `Closes #<번호>`는 기본 브랜치(`dev`)에 병합될 때 이슈를 자동으로 닫는다.
- 작업 중에 `dev`가 앞서 나가면 `git fetch github` 뒤 작업 브랜치에서 `git merge github/dev`로 따라잡는다. 강제 푸시는 쓰지 않는다.
- 검사 그룹은 `docs/테스트_하네스.md` 분기표가 정한다.

## 4. 릴리스: `dev` → `main` → axhub

언제: 앱이 바뀌어 사이트에 올려야 할 때, 그리고 제출 전 마지막에. 문서만 바뀐 경우는 다음 릴리스로 미뤄도 된다.
릴리스도 이슈 → 드래프트 PR → 자체 리뷰 → 종료 순서를 따른다.

```powershell
git switch dev; git pull; git fetch github
git log --oneline github/main..github/dev      # 이번에 나갈 변경
gh issue create --title "release: <날짜> <요약>" --body "<포함 PR 목록, 확인할 화면>"
python tools/selftest.py all                   # 배포 전 전체 검사
gh pr create --draft --base main --head dev --title "release: <날짜> <요약>" --body "Refs #<번호> ..."
# 자체 리뷰: git diff github/main...github/dev 확인 → 리뷰 댓글 → gh pr ready
gh pr merge <PR번호> --merge                   # merge commit. --delete-branch는 붙이지 않는다
git switch main; git pull github main
git push origin main                           # axhub 자동 배포
git ls-remote --heads github dev               # dev가 남아 있는지 확인
# 사이트 /healthz와 바뀐 화면 확인 → 결과를 이슈 댓글로 남기고 gh issue close <번호>
```

- 릴리스 PR은 기본 브랜치가 아닌 `main`으로 병합되므로 이슈를 자동으로 닫지 않는다. 배포를 확인한 뒤 손으로 닫는다(본문은 `Closes` 대신 `Refs`).
- **merge commit을 쓰는 이유:** squash하면 `main`에만 있는 커밋이 생겨 다음 릴리스 PR에 이미 배포한 변경이 다시 보이거나 충돌한다. merge commit이면 `dev`의 커밋이 그대로 `main` 이력에 들어간다.
- **자동 브랜치 삭제를 끈 이유:** 켜 두면 릴리스 PR 병합 때 head인 `dev`가 지워질 수 있다. GitHub 문서에 기본 브랜치 예외가 없고, 이 저장소는 브랜치 보호를 쓸 수 없다. 그래서 작업 PR만 `--delete-branch`로 지운다.
- 훅은 GitHub의 `main`(로컬 `github/main`)과 다른 커밋을 axhub에 올리지 못하게 막는다. 병합하지 않은 코드가 배포되는 일을 막기 위해서다.

## 5. 지킴이

| 장치 | 막는 것 |
|---|---|
| pre-push 훅 `tools/git-hooks/pre-push` | 이름 규칙에 안 맞는 브랜치 푸시 · GitHub `main`·`dev` 직접 푸시와 삭제 · axhub에 `main` 아닌 브랜치 푸시와 `main` 삭제 · GitHub `main`과 다른 커밋의 axhub 배포 |
| `python tools/selftest.py guard` | 훅 미설치·CRLF 섞임 · 현재 브랜치 이름 규칙 위반 · `main`·`dev`에서 스테이징한 변경 |
| GitHub 저장소 설정 | 기본 브랜치 `dev` · 병합 방식 squash와 merge commit만(rebase 끔) · 자동 브랜치 삭제 끔 · Actions 끔 |

- 훅 설치(새로 clone하면 한 번): `git config core.hooksPath tools/git-hooks`
- 훅은 sh로 돈다. `.gitattributes`가 `tools/git-hooks/` 파일을 LF로 고정해 Windows(`core.autocrlf=true`)에서도 깨지지 않는다.
- `--no-verify`로 훅을 건너뛰는 것은 사용자 확인을 받은 뒤에만 한다.
- `gh issue develop`은 GitHub API로 브랜치를 만들어 훅을 거치지 않는다. 이름은 첫 푸시(빈 커밋) 때 훅이, 작업 중에는 `guard`가 확인한다.

## 6. 한 번 한 설정 (11/09)

- `dev`를 `main`(c7960a9)에서 만들어 GitHub에 올렸다. 로컬 `dev`는 `github/dev`를, `main`은 `github/main`을 추적한다.
- GitHub: 기본 브랜치 `main` → `dev`, merge commit 허용, 자동 브랜치 삭제 끔.
- 로컬: `core.hooksPath = tools/git-hooks`
- axhub `origin`의 `main`은 아직 949f066(템플릿 + `.gitignore` 복구)이다. 첫 릴리스 때 그 뒤의 커밋이 함께 올라간다(리서치·분석 문서는 PR #10에서 git에서 빠져 이력에만 남는다). Dockerfile이 앱 파일만 복사하므로 사이트 동작은 바뀌지 않는다.
